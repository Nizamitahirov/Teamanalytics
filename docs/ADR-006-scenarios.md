# ADR-006 — Ssenarilər, balanslama, təsdiq axını (Mərhələ 6)

**Tarix:** 2026-11-20 · **Status:** qəbul edilib (PR gözləyir) · **Əlaqəli:** SPEC §2, §6.5, §8, §4.4, §4.5

## Nə quruldu
- **Ssenari modeli** (`shared/scenario.ts`): ssenari = ad + dəyişikliklər siyahısı. Hər dəyişiklik (`ScenarioChange`) bir və ya bir neçə **upsert Op**-dur (`Tasks` / `Employees` / `Settings`) + `base` — dəyişiklik yaradılanda **canlı datadakı** köhnə dəyərlər. Ssenari datası = canlı data + op-ların lokal tətbiqi (`shared/apply.ts → applyOpsTo`, upsert yalnız göndərilən sahələri dəyişir — server `updateMask` semantikası ilə eyni).
- **Dəyişiklik növləri**: ötür, ləğv et / bərpa, saatı dəyiş, yeni iş, əməkdaş əlavə et, əməkdaş çıxır (`active=false`, silinmir), ştatı dəyiş, normanı dəyiş, prosesi avtomatlaşdır (−X%). Ötürmə v1 qaydasını saxlayır (`owner_before` ilkin sahib, `owner_after` yeni).
- **Şablonlar**: boş, əməkdaş ayrılır (çıxır + işləri alqoritmlə paylanır), yeni əməkdaş gəlir (+ balanslama), prosesi avtomatlaşdır, yükü balansla, normanı dəyiş.
- **Balanslama** (`shared/rebalance.ts`, SPEC §8): deterministik greedy — donorlar azalan yükə görə, işləri artan saata görə, qəbul edən `yük + h/cap ≤ θ − 0,05`, ən aşağı nəticə yükü; bərabərlikdə prosesi artıq görən, sonra ad. Seçimlər: θ (100% / warn%), eyni şirkət (default açıq, S3), eyni fəaliyyət forması, kilidli işlər, `evacuate` (ayrılan əməkdaş). Nəticə **heç vaxt birbaşa tətbiq olunmur** — ssenari dəyişiklikləri kimi açılır; hər təklif ayrıca dəyişiklikdir (çıxar / kilidlə).
- **Müqayisə**: `compare(live, scen)` — KPI-lar `computeMetrics` ilə (§7 formulaları, tək mənbə), əməkdaş üzrə yük əvvəl/sonra; 2–3 ssenari yan-yana (`/scenarios/compare?ids=`).
- **Tətbiq** (klient): `findConflicts` ssenari yaradılandan sonra canlı datada dəyişmiş sənədləri tapır (`base` ≠ indiki dəyər, sənəd silinib, yeni sənəd artıq var). Default: ziddiyyətli dəyişiklik **buraxılır**, istifadəçi "yenə də tətbiq et" seçə bilər. Sonra **bir `commit`** — adi sinxron axını (diffOps → /api/ops, versiya yoxlaması), tək "Geri al" ilə qayıdır; jurnalda başlıq "Ssenari: X tətbiq edildi" + hər sənəd üzrə alt qeydlər (`comment: Ssenari: X`). Növbə boşalandan sonra `POST /api/scenarios {action:'applied'}`.
- **Server**: `api/scenarios.ts` (GET viewer+; create/update/delete/archive/restore/submit — editor+, yalnız müəllif və ya admin dəyişir/silir; reject — admin; applied — editor+, təsdiq axını açıqdırsa yalnız admin), `api/notifications.ts` (öz bildirişlərim, oxunmuş et — yalnız özününkü).
- **Təsdiq axını** (SPEC §2, S1 — default **söndürülü**): ayarlar `approval` (0/1), `approval_hours` (40). Açıqdırsa: editor ssenarini tətbiq edə bilmir → "Təsdiqə göndər" → bütün aktiv adminlərə bildiriş → admin "Təsdiqlə və tətbiq et" və ya "Rədd et" (müəllifə bildiriş). Ötürmə dialoqunda həddi aşan ötürmə avtomatik ssenari kimi təsdiqə gedir. **Server qoruması:** `/api/ops`-da editor-un bir partiyadakı ötürmələrinin cəmi həddi aşırsa → 403 `approval_required`.
- **Bildirişlər**: üst paneldə zəng (oxunmamış sayğac), siyahı, keçid, "hamısını oxunmuş et".

## Qərarlar / kompromislər
1. **Ssenari yazıları məlumat sinxronuna toxunmur.** `meta.updated` yenilənsəydi, hər ssenari yaddaşı bütün açıq klientlərdə delta sorğusu (3 oxuma) yaradardı. Əvəzinə `meta.scen_ts` yenilənir; `/api/data` onu hər cavabda (əlavə oxumasız) qaytarır, klient fərq görəndə `/api/scenarios`-u oxuyur (ssenarilər + son 300 bildirişdən özününkülər). Boş yoxlamada əlavə oxuma **0**.
2. **Dəyişikliklər JSON sətri kimi** (`scenarios/{id}.changes`) — Firestore klientimiz yalnız skalyar dəyərlər yazır; ≤ 3000 op və ≤ 900 KB (sənəd limiti 1 MiB).
3. **Tətbiq klientdə**, serverdə ayrıca "apply" endpoint-i yox: adi `/api/ops` yolu versiya ziddiyyəti, offline növbə, undo və jurnal məntiqini təkrar yazmadan istifadə edir. Server ssenarinin statusunu yalnız qeyd edir.
4. **Təsdiq axınının server qoruması yalnız ötürmələr üçündür** (SPEC "40+ saatlıq ötürmə"). Editor-un ssenari tətbiqinə qadağa UI-da və `applied` statusundadır; editor ayrı-ayrı ləğv/saat dəyişikliklərini onsuz da birbaşa edə bilir (SPEC buna qadağa qoymur). Hədd partiya üzrədir.
5. **"Əməkdaş çıxır" silmə deyil** — `active=false` (bərpa oluna bilər; `end_date` sahəsi Mərhələ 7+).
6. **"Əvvəl" rəngi boz qalır** (`#A3A7B7`, CLAUDE.md §8): dataviz validatoru "xroma aşağı" deyir — qəsdəndir (müqayisə bazası fon kimi oxunmalıdır); açıq rejimdə kontrast < 3:1 — hər bar cədvəl sətrindədir və faiz mətni yanındadır (rəng tək daşıyıcı deyil).

## Sahibin diqqətinə (rəqəm deyil, data məsələsi)
Seed-də balanslama 26 ötürmə təklif edir (Ülkər 113→97%, Sveta x 113→98%, Ağaəli 106→98%) və işlərin bir hissəsini **hazırda heç bir işi olmayan** profillərə verir: Fəridə (Farida-nın dublikatı ehtimalı), Orxan, Aygül, İqrar. Nəticədə "Mövcud ştat" 18 → 22 olur (formula düzgündür: aktiv işi olanların ştatı). Bu profillərin real vəziyyəti (dublikat? layihə işçisi?) Mərhələ 7-də (Data sağlamlığı) həll olunacaq; o vaxta qədər təklifi redaktorda çıxarmaq və ya kilidləmək olar.
